## 1) Один способ компиляции/запуска backend’а. Всегда.

**Правило:** backend (Nest) в dev должен запускаться **только через Nest CLI / tsc**, не через tsx/ts-node без метаданных.

Почему: Nest DI на классах с типами очень часто опирается на `emitDecoratorMetadata`. Когда ты запускаешь через “левый” раннер (tsx), ты можешь получить:

- `design:paramtypes` не эмитится,
    
- DI начинает инжектить `undefined`,
    
- дальше “Cannot read properties of undefined (reading 'get')”.
    

✅ Рекомендация:

- `dev`: `nest start --watch` (или `nest start api --watch` если monorepo/workspaces)
    
- `build`: `nest build`
    
- никаких `tsx watch src/main.ts` для Nest приложения
    

---

## 2) В monorepo — чёткая точка входа Nest CLI

**Правило:** Nest CLI должен “видеть” правильный `tsconfig` и `nest-cli.json`, иначе он пытается искать `apps/api/tsconfig.json` относительно workspace корня и падает.

✅ Два рабочих режима:

1. **Nest workspace режим** — корневой `nest-cli.json`, который знает про `apps/api`
    
2. **Standalone режим** — запускать CLI из `apps/api` с локальным `nest-cli.json` и `tsconfig.json`
    

Если у тебя _нет_ корневого `nest-cli.json`, то:

- запускай `pnpm --filter @leadership-architect/api dev` из корня,
    
- либо запускай `pnpm dev` **строго из `apps/api`**, но с корректным `nest-cli.json`.

## 3) Prisma: никогда не создавай relation через `*_id`, если schema этого не позволяет

**Правило:** если Prisma ругается `entry_id: never`, значит в `CreateInput` нельзя писать `entry_id`, нужно писать:

`entry: { connect: { id: entryId } }`

Это правило спасает от 30% “почему тип never??”.

✅ Запомнить:

- `CreateInput` = через `connect`
    
- `UncheckedCreateInput` = иногда позволяет `*_id`, но это “нож в спину”, если не договориться, что вы используете его осознанно
    

---

## 4) DTO и сервисные типы должны быть связаны. “string” запрещён для enum-полей.

**Правило:** в DTO нельзя оставлять `type: string`, если по системе это union.

У тебя это вылезло в:

- Evidence.type
    
- Quest.type
    

✅ Железно:

- В DTO: `type: 'micro' | 'weekly' | ...`
    
- Плюс в runtime валидация (`@IsIn([...])`) — иначе типы помогут только компилятору, но не API.
    

---

## 5) “Optional” в DI — только если ты реально готов жить без зависимости

**Правило:** `@Optional()` на сервисе — это не “пофиксим ошибку”. Это архитектурное решение: **сервис способен работать без этой зависимости**.

Иначе ты получаешь “мок-режим”, “если нет — пропускаем”, а потом другой сервис говорит “критическая ошибка”.

✅ Как правильно:

- если зависимость обязательна — **никаких Optional**, ошибка должна быть на старте через Nest, а не через `Cannot read get`.
    
- если зависимость временная (например QuestGenerationService) — убирай не только из конструктора, но и весь код, который её использует, либо делай `if (!dep) return`.
    

---

## 6) Никогда не “гаси” ошибки в конструкторе сервиса

**Правило:** try/catch в конструкторе, который “проглатывает” проблему и продолжает в mock-mode — это ловушка.

Почему: Nest считает провайдер успешно созданным, но состояние внутри “полумёртвое”. Потом ломается в другом месте, и дебажить ад.

✅ Что делать:

- Конструктор делает только инициализацию полей
    
- Валидация env/конфигов — в отдельном `onModuleInit()` или на уровне `ConfigModule validationSchema`
    
- Если конфиг критичен — **throw сразу**, пусть приложение не стартует

## 7) Всегда отделяй “типовую компиляцию” от “запуска”

**Правило:** Сначала проект должен собираться TypeScript’ом. Потом запускаться.

У тебя было: попытка запустить — и в процессе выясняется 99 ошибок.

✅ Режим работы:

- `pnpm -C apps/api typecheck` (или `tsc --noEmit`)
    
- потом `pnpm -C apps/api dev`

## 8) У тебя сейчас две системы правды: Prisma schema vs код

**Правило:** Prisma schema — источник истины, а код должен адаптироваться.

Если Prisma требует `user` relation, то:

- или ты везде подключаешь `user: connect`
    
- или меняешь Prisma schema (делаешь user optional)  
    Но нельзя оставлять “то так, то так”.
    

---

## 9) Тестовые файлы должны быть исключены из сборки API (если они не настроены)

**Правило:** если у тебя `.spec.ts` попадают в компиляцию и валят dev — исключай их из `tsconfig` или подними jest types.

Самый быстрый стабильный вариант:

- исключить `**/*.spec.ts` из `apps/api/tsconfig.json`
    
- отдельно настроить тестовый tsconfig, если нужно
    

---

## 10) Один тип — одно место

**Правило:** если у тебя `CreateQuestDto` импортируется “из двух разных путей” и TypeScript считает это разными типами — значит у тебя проблема с **paths/alias** и импортами.

✅ Запомнить:

- DTO должны импортироваться только из одного источника (например `src/common/dto`)
    
- для shared типов — отдельный пакет `packages/shared` и единый alias
    
- не смешивать относительные пути и алиасы вперемешку

# Практическое правило “чтобы не тонуть”

Если выбрать 3 самые важные вещи, чтобы больше не попадать в такие штопоры:

1. **Один запуск**: Nest CLI, без tsx
    
2. **Контракты**: DTO union’ы + Prisma relations через connect
    
3. **Никаких моков/try-catch в конструкторе** для скрытия проблем — только fail-fast
