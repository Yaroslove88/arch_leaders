## 🎯 Цель аудита

Провести полный технический и архитектурный аудит проекта с целью:

- выявить критические и системные проблемы в кодовой базе
    
- восстановить целостность архитектуры
    
- привести проект в компилируемое, стабильное и масштабируемое состояние
    
- подготовить план рефакторинга и развития
    

Результат аудита должен дать ясную картину:

- **что сломано**
    
- **почему сломано**
    
- **что обязательно исправить**
    
- **что можно улучшить**
    
- **в каком порядке это делать**
    

---

## 🧩 Объект аудита

Проект в целом, включая:

- Backend (NestJS, Prisma, LLM, Sync, Admin, Tree, Quests и т.д.)
    
- Архитектуру модулей
    
- Схему данных (Prisma)
    
- Dev-инфраструктуру (tsconfig, nest-cli, запуск, сборка)
    
- Типизацию и контракты
    
- Интеграции (JWT, Config, LLM, внешние API)
    
- Качество кода и инженерные практики
    

---

## 🔍 Области аудита

### 1️⃣ Архитектурный аудит

Проверить:

- корректность модульной структуры NestJS
    
- зависимости между модулями (циклы, утечки, God-modules)
    
- разграничение слоёв:
    
    - controllers
        
    - services
        
    - domain logic
        
    - infrastructure (prisma, llm, integrations)
        
- соответствие архитектуре (если она задумывалась)
    
- целостность bounded contexts (entries, evidence, quests, sync, tree, admin, auth…)
    

Результат:

- карта архитектуры
    
- список архитектурных нарушений
    
- рекомендации по реструктуризации
    

---

### 2️⃣ Аудит сборки и инфраструктуры

Проверить:

- tsconfig (root + apps/api)
    
- nest-cli.json
    
- dev/build/start скрипты
    
- использование tsx / ts-node / nest-cli
    
- consistency outDir / paths / monorepo
    
- корректность decorator metadata
    
- environment management (.env, ConfigModule)
    

Результат:

- эталонная dev-схема запуска
    
- эталонная build-схема
    
- список инфраструктурных проблем
    
- рекомендации по стабилизации среды
    

---

### 3️⃣ Аудит типизации и контрактов

Проверить:

- DTO ↔ Service ↔ Prisma соответствие
    
- наличие “string вместо union”
    
- any/unknown/implicit contracts
    
- рассинхроны DTO и domain-типов
    
- нарушение Liskov/контрактов сервисов
    
- unsafe касты
    
- дубли типов
    

Результат:

- список типовых конфликтов
    
- карта контрактов системы
    
- предложения по унификации типов
    

---

### 4️⃣ Аудит Prisma и модели данных

Проверить:

- схему Prisma
    
- обязательные связи (user, entry, session и т.д.)
    
- где нарушены create/connect паттерны
    
- корректность relation-архитектуры
    
- соответствие бизнес-логике
    
- миграционную историю
    
- naming (entry_id vs entry.connect)
    

Результат:

- ER-диаграмма фактической модели
    
- список несоответствий кода и схемы
    
- рекомендации по пересборке data layer
    

---

### 5️⃣ Аудит доменной логики

Проверить ключевые домены:

- Entries / Evidence
    
- Sessions / Analysis
    
- Quests / Abilities
    
- Tree / ChangeLog
    
- Admin / Auth / Prompts
    

На предмет:

- смешения ответственности
    
- утечек инфраструктуры в домен
    
- отсутствия domain-моделей
    
- хаотичных сервисов
    
- неявных инвариантов
    

Результат:

- доменная карта системы
    
- найденные логические разрывы
    
- предложения по выстраиванию domain-layer
    

---

### 6️⃣ Аудит LLM-интеграции

Проверить:

- слой абстракции над LLM
    
- управление провайдерами
    
- работу с ошибками
    
- детерминированность контрактов
    
- fallback-механику
    
- безопасность
    
- воспроизводимость
    

Результат:

- оценка зрелости LLM-слоя
    
- рекомендации по превращению в стабильный subsystem
    

---

### 7️⃣ Аудит качества кода

Проверить:

- уровень связности
    
- дублирование
    
- наличие “магии”
    
- нарушение SRP
    
- тестопригодность
    
- технический долг
    
- code smells
    

Результат:

- список системных проблем
    
- hotspots проекта
    
- quick wins
    
- долгосрочные зоны риска
    

---

## 📦 Формат результатов

Аудит должен завершиться артефактами:

### ✅ 1. Audit Report (основной документ)

Структура:

1. Executive summary
    
2. Карта текущего состояния системы
    
3. Ключевые риски
    
4. Архитектурные проблемы
    
5. Инфраструктурные проблемы
    
6. Data / Prisma проблемы
    
7. Типизация и контракты
    
8. LLM и интеграции
    
9. Технический долг
    
10. Приоритетный roadmap
    

---

### ✅ 2. Технический бэклог

Таблица или board:

- проблема
    
- модуль
    
- уровень критичности (blocker / high / medium / low)
    
- тип (architecture / infra / data / logic / cleanup)
    
- рекомендуемое решение
    
- порядок внедрения
    

---

### ✅ 3. Целевая архитектурная схема

- слои
    
- модули
    
- домены
    
- data flow
    
- границы ответственности
    

---

### ✅ 4. План стабилизации

Пошаговый план:

**Фаза 1 — Stabilization**

- сборка
    
- типы
    
- Prisma
    
- DI
    
- contracts
    

**Фаза 2 — Architecture cleanup**

- модули
    
- домены
    
- сервисы
    
- data-layer
    

**Фаза 3 — System design**

- LLM subsystem
    
- sync/analysis pipeline
    
- quest engine
    
- tree engine

## 🎯 Критерии успешности

Аудит считается успешным, если после него:

- понятно, **что за система реально существует**
    
- понятно, **почему она сейчас ломается**
    
- есть **очерёдность действий**
    
- появляется **контроль над сложностью**
    
- можно безопасно развивать продукт
