# 🏗 TECH ARCHITECTURE AUDIT CHECKLIST

_(для AI-driven product, evolving system)_

---

# I. 🧱 СТРУКТУРА ПРОЕКТА И КОДА

### 1. Границы доменов

-  Проект разбит по **доменам**, а не по типам файлов  
    (users / entries / analysis / abilities / quests / admin / jobs / ai / configs).
    
-  Каждый домен имеет:
    
    - свой модуль
        
    - свои entity / service / repository / controller
        
-  Нет “god-services” (AnalysisService на 2000 строк).
    

### 2. Dependency direction

-  Домены не тянут друг друга циклически.
    
-  AI / LLM слой — инфраструктура, не ядро.
    
-  Admin — отдельный BFF, не пролезает в core-логику.
    
-  Core (ability, quest, changelog) не знает о UI и Telegram.
    

### 3. Папочная архитектура

-  `core/` (domain + application logic)
    
-  `infra/` (db, queue, llm, telegram, storage)
    
-  `interfaces/` (api, admin, bot)
    
-  `shared/` (types, events, errors)
    

Внутри домена:

```
abilities/
  ability.entity.ts
  ability.service.ts
  ability.engine.ts   ← бизнес-правила
  ability.repository.ts
  ability.controller.ts
  dto/
  tests/
```

---

# II. 🧠 ДОМЕННАЯ МОДЕЛЬ

### 4. Ясность сущностей

-  Entry ≠ Session ≠ Evidence ≠ ChangeLog.
    
-  AbilityNode (каталог) ≠ UserAbilityState (состояние).
    
-  QuestTemplate (если будет) ≠ QuestInstance.
    
-  Нет “универсальных таблиц”.
    

### 5. Состояние vs события

-  Есть разделение:
    
    - event data (entries, evidence, artifacts)
        
    - state (user_ability_state, active quests).
        
-  Любое изменение состояния можно объяснить через события.
    
-  ChangeLog — не лог, а доменная сущность.
    

### 6. Версионирование

-  Session artifacts версионируются.
    
-  Prompts версионируются.
    
-  Config формул версионируется.
    
-  Ability changes содержат версию формул.
    

---

# III. 🔁 PIPELINE И JOB ARCHITECTURE

### 7. Асинхронность

-  Любой анализ — job.
    
-  Любой пересчёт — job.
    
-  Любая массовая операция — job.
    
-  Нет тяжёлой логики в HTTP-request.
    

### 8. Идемпотентность

-  Job можно безопасно перезапустить.
    
-  Повторный анализ не ломает состояние.
    
-  Есть deduplication ключи.
    

### 9. Стадийность

-  Анализ разбит на этапы:  
    preprocess → interpret → synthesize → update → quest.
    
-  Можно перезапустить этап.
    
-  Можно отключить этап.
    

---

# IV. 🤖 AI / LLM КОНТУР

### 10. Изоляция AI

-  LLM вызывается только через один слой (LLMService / AIAdapter).
    
-  Промпты не захардкожены в бизнес-логике.
    
-  Выход LLM всегда проходит schema-validation.
    

### 11. Трассировка

-  Логируются:
    
    - входы
        
    - промпт id + версия
        
    - модель
        
    - выход
        
    - ошибки
        
-  Можно восстановить, как был получен результат.
    

### 12. Fallbacks

-  Есть режим:
    
    - без обновления дерева
        
    - без генерации квестов
        
    - summary-only.
        
-  Ошибка LLM не рушит систему.
    

---

# V. 🌳 ABILITY & QUEST ENGINE

### 13. Business rules отдельно

-  Формулы не внутри контроллеров.
    
-  AbilityEngine — отдельный слой.
    
-  QuestEngine — отдельный слой.
    
-  Правила читаются как спецификация.
    

### 14. Deterministic core

-  Из одинаковых входов — одинаковый state.
    
-  AI даёт сигналы, но не принимает финальных решений.
    
-  AbilityEngine можно прогнать без LLM.
    

---

# VI. 🗃 ДАННЫЕ И ХРАНЕНИЕ

### 15. Целостность

-  FK реально используются.
    
-  Нет “висячих” ссылок.
    
-  Evidence и Entry не удаляются без политики.
    

### 16. Производительность

-  Индексы под User 360.
    
-  Отдельные read-модели для админки.
    
-  Нет N+1 в критических местах.
    

### 17. Миграции

-  Все изменения через миграции.
    
-  Версии схемы связаны с версиями кода.

# VII. 🛡 БЕЗОПАСНОСТЬ И НАДЁЖНОСТЬ

### 18. Доступ

-  Отдельные таблицы admin_users.
    
-  RBAC.
    
-  Sensitive access логируется.
    

### 19. Секреты

-  Ключи не в коде.
    
-  Ротация возможна.
    
-  Отдельные env для admin.
    

### 20. Надёжность

-  Retries с backoff.
    
-  Dead letter queue.
    
-  Alerting.

# X. 🚨 КРАСНЫЕ ТЕХНИЧЕСКИЕ ФЛАГИ

Если ты видишь это — архитектура начинает деградировать:

-  контроллеры содержат бизнес-логику
    
-  LLM напрямую пишет в базу
    
-  нет единого места формул
    
-  нельзя объяснить, откуда взялся квест
    
-  нельзя безопасно пересчитать пользователя
    
-  “всё в одном сервисе”
    
-  изменения состояния без change_log
