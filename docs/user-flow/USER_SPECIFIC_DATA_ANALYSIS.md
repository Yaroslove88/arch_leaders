# Анализ системы: где нужно учитывать пользователя

## ✅ Уже исправлено

### 1. Quest Completion (quests.service.ts)
- **Проблема**: При завершении квеста exp начислялся на глобальное дерево
- **Исправление**: Теперь передается `userId` в `updateNodeProgress`
- **Статус**: ✅ Исправлено

### 2. Tree Service (tree.service.ts)
- **Проблема**: `updateNodeProgress` и `applyChange` работали только с глобальным деревом
- **Исправление**: 
  - `updateNodeProgress` принимает `userId?` и работает с пользовательским деревом
  - `applyChange` принимает `userId?` и создает/обновляет пользовательское дерево (`tree_user_${userId}`)
- **Статус**: ✅ Исправлено

### 3. Tree Controller (tree.controller.ts)
- **Проблема**: Не передавал `userId` в методы сервиса
- **Исправление**: Методы `updateNode` и `applyChange` получают `userId` из токена
- **Статус**: ✅ Исправлено

## ⚠️ Потенциальные проблемы

### 1. Ability State Service (ability-state.service.ts)
- **Текущее состояние**: Работает с `userAbilityState` (пользовательские данные) ✅
- **Анализ**: 
  - `UserAbilityState` и `TreeSemantic` - это **две разные системы** с разными целями
  - `TreeSemantic` - хранит полное дерево с XP и состоянием (источник истины для отображения)
  - `UserAbilityState` - хранит аналитическое состояние с `relevance` (для анализа сессий)
- **Решение**: 
  - ✅ Реализована минимальная синхронизация: при обновлении `state` в `TreeSemantic` → автоматически обновляется `state` в `UserAbilityState`
  - ✅ `UserAbilityState` обновляет только `relevance` и `progress`, не перезаписывает критичные состояния (`locked`/`unlocked`/`integrated`)
  - ✅ `TreeSemantic` является источником истины для `state`
- **Документация**: 
  - Подробный анализ: `docs/ABILITY_STATE_ARCHITECTURE_ANALYSIS.md`
  - Реализация: `docs/SYNC_IMPLEMENTATION.md`
- **Статус**: ✅ Исправлено

### 2. Quest Generation (quest-generation.service.ts)

### 5. Builds Service (builds.service.ts)
