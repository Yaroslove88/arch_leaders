### 4️⃣ Недостающие структурные элементы для новой философии

**В структуре не хватает:**
- блока meta с допуском, зрелостью, pressure, subjectivity_load, systemic_regress_risk, marker_icons
- секций event, facts, background как отдельных структурных ключей
- “positions” взамен «options» — философски более точная формулировка
- у reflection не хватает градации по итогам выбора, побочных последствий, “страт-ходов”
- маркеров архетипа/символа/уровня “входа в ситуацию”
- возможности разделения «факты»/«гипотезы»/«глубинный фон»

**В контенте не хватает:**
- явного выделения части информации в новые секции (контекст, событие, факты, фон, дилемма)
- строгих метаданных (много где часть нужных данных есть только внутри «context» обычным текстом)
- новых индикаторов зрелости, поля, нагрузки, допусков в “meta”
- отсутствует дифференциация управленческих позиций — есть только абстрактные «options»

### 3. Пояснение по каждой зоне (как заполнять)

- **meta:**  
  - Точное “досье”: структура и позиционирование кейса, все ключевые показатели, индикаторы.  
  - Использовать коды и тэги бренда.
- **portal:**  
  - “Вход” в ситуацию — чувство профессионального пространства.  
  - Без эмодзи, только строгие маркеры и access-бары.
- **event:**  
  - Выделять только Событие/Триггер, отделяя от всего кейса.  
  - Яркий контейнер, кратко и с ощущением срочности.
- **context:**  
  - Карта поля системы, не просто “описание”.  
  - Описывать отдельно основные элементы среды.
- **facts:**  
  - Только проверяемые факты (“что есть”), все интерпретации убирать в background.
- **background:**  
  - Использовать как психологический или литературный фон для создания глубины вступления (collapsible).
- **dilemma:**  
  - Ядро, формулировать как экзистенциальную развилку управленца, без явного решения.
- **positions:**  
  - Описывать не только действия, а именно позиции (варианты смысловых стратегий управления), возможный тип хода (управление, делегирование, созидание, выдерживание и др.)
- **indicators:**  
  - Вынести все показатели зрелости, неопределённости, нагрузки и рисков в отдельный блок.
- **reflection:**  
  - Прорабатывать глубже: вопросы после выбора, инсайты, зеркала для зрелости.

## System Prompt/Шаблон для генерации кейсов в парадигме "инициационного пространства"

---

### I. Инструкция для ИИ: Как создавать кейсы новой системы

**Роль:**  
Ты — интеллектуальный архитектор управления и зрелости. Генерируешь кейсы, моделирующие путь управленца в сложной системе. Каждый кейс — не игровая задача, а стратегический симулятор мышления и выбора позиции.

**Общее правило:**
- Структурируй кейс по секциям: meta, portal, event, context, facts, background, dilemma, positions, indicators, reflection.
- Иерархия и архитектура важнее повествовательности!
- Каждый уровень кейса — не "сложность", а новая глубина лидерской субъектности.

---

#### 1. meta  
- Явно вывожу все ключевые индикаторы (допуск, зрелость, уровень давления, нагрузка, символы).
- Использую только строгие, осмысленные метки.
- Все значения в meta должны соответствовать смысловому бренду (архитектор, стратег, советник).

#### 2. portal  
- Это досье и профессиональный вход в ситуацию.  
- Ощущение рабочего кабинета или стратегического зала.
- Никаких emoji — только символы, метки, аббревиатуры.

#### 3. event  
- Событие — отдельная зона фокуса. Не пропускай!
- Краткая сцена, желательно с датой/моментом напряжения.

#### 4. context  
- Поле системы.  
- Разбивай: среда, ограничения, люди, режим работы — не сливай в "бэкграунд".
- Формулировки избегают бытовых и игровых паттернов.

#### 5. facts  
- Только факты: ролевая карта поля без эмоций.
- Проверяемость выше чувств.

#### 6. background  
- Психологический/литературный фон. Описывает «нагрузку субъекта» или глубинный смысл, который влияет на выбор, но не очевиден.
- Делай эту секцию сворачиваемой, не слишком длинной.

#### 7. dilemma  
- Экзистенциальная управленческая развилка.  
- Всегда требует не решения, а позиции субъекта — свобода вынести напряжение выбора.

#### 8. positions  
- Не просто "варианты" — каждая позиция = стратегический управленческий ход (например: “Делегировать”, “Выдержать напряжение”, “Вмешаться лично”).
- Обязательно прописывать тип позиции и краткое последствие на трёх уровнях: immediate, second_order, systemic.
- Для каждой позиции — короткая reflection_prompt (“Зачем ты выбрал именно это?”).

#### 9. indicators  
- Индикаторы зрелости, нагрузки на субъекта, системных рисков и уровня неопределённости.
- Заполняются раздельно по смыслу секций, а не для красоты.

#### 10. reflection  
- 2-5 глубоких вопросов — прежде всего на рефлексию выбора, выдержки уровня, умение работать в неопределённости.
- after_choice_insights — короткие готовые формулировки-результаты после выбора (what you learn by taking this position).

---

### II. Генерируемый результат (output expected, на английском/rus):

- Только структурированный markdown или JSON в утверждённом формате;
- Каждый блок начинается с ключа (как в схеме);
- Не вставлять лишних повествований и не усложнять вводные.

---

### III. Правила соответствия и философские ограничения

- Не допускать бытового, инфантильного или игрового описания.
- Кейс должен моделировать стратегическую управленческую развилку, а не моральную историю или кейс на “логические ошибки”.
- Всегда: первичны глубина и напряжение, вторично — привычные бытовые action-choices.
- Факт и интерпретация всегда отдельно.
- В дилемме нет “правильного” выбора, только рабочие позиции, отражающие зрелость или регресс субъекта.

### 2. Требования к UI и дизайну (синтетика по бренду)

- **Общее чувство**: тёмная архитектурная плоскость, крупные пустоты (воздух), строгие линии-разделители, лёгкие созидательные glows, акценты золотом/янтарём на важных реактивных местах.
- **Контейнеры внутри:** явные ниши, блоки визуально разнесены, перевес на графитовые/обсидиановые оттенки.
- **Фон:** глубокий тёмный с лёгкими тенями.
- **Линии**: тонкие, с намёком на премиум.
- **Заголовки:** крупные, разреженные, не навязчивые; не декоративные шрифты.
- **Иконки/символы:** символические архетипы вместо emoji; допускаются спец. шифры, если вписаны в гайд.
- **Событие (event):** контейнер светлее фона, с янтарным (amber) акцентом.
- **Контекст (context):** графитовый, мягкая тень, чёткая сетка внутри (таблица/grid).
- **Факты (facts):** строгий холодный (strategic blue), минимализм.
- **Фон/История (background):** Collapsible, фиолетовые и серые полутона, на втором плане.
- **Дилемма:** обрамлено рамкой, контраст с фоном, насыщенное “молчанием/воздухом”.
- **Позиции (positions):** акцентные заголовки, крупные кнопки.
- **Рефлексия:** специальный контейнер, возможно цвет “system-focus”.
- **Не показывать лишних украшений, инфо-шума или геймификации (аксессуары только по реальной структуре).**

**Этап 4:** Чек-лист валидатора кейса по новой системе

## Чек-лист валидатора для кейса “инициационного пространства”

### 1. Структурная полнота
- [ ] Присутствуют ВСЕ ключевые секции структуры: `meta`, `portal`, `event`, `context`, `facts`, `background`, `dilemma`, `positions`, `indicators`, `reflection`
- [ ] Нет никакой секции из старой структуры, не имеющей смыслового маппинга в новую (устаревший context/history/options/reflection без разметки)

### 2. Качество контента
- [ ] Секция `meta` включает: уникальный идентификатор, node_id, branch_id, access_level, maturity_level, symbols, pressure_level, uncertainty, subjectivity_load, systemic_regress_risk
- [ ] В портале нет emoji и бытовых “шапок” — только маркировки/символы/архитипы/уровень допуска
- [ ] Секция `event` выделена, содержит лаконичное описание триггера/инцидента/события, уровень срочности — ОТДЕЛЕН ОТ КОНТЕКСТА
- [ ] В контексте выделены company, environment, constraints, people, mode
- [ ] В секции `facts` — только проверяемые объективные факты, интерпретации и эмоции вынесены в `background`
- [ ] `background` несёт литературный, субъективный, психологически нагружающий слой, имеет признак “collapsible”
- [ ] Секция `dilemma` формирует “ядро неопределённости” — позиционный конфликт или развилка, без “очевидного” решения
- [ ] В каждом кейсе не менее 2 и не более 5 позиций (sections `positions`), каждая = стратегический ход, не абстрактный поступок
- [ ] По каждой позиции прописаны: type, immediate, second_order, systemic consequence, reflection_prompt
- [ ] Заполнены индикаторы: зрелость, уровень неопределённости, нагрузка на субъекта, системный риск (отдельная секция)
- [ ] В `reflection` — минимум 2 глубоких вопроса, минимум 2 after_choice_insights, всё по делу выбранной позиции

### 3. Бренд/философия и визуальная логика
- [ ] Нет бытовых, инфантильных, игровых паттернов (даже в формах вопросов)
- [ ] Факт и интерпретация в разных секциях
- [ ] В дилемме нет моральных оценок, только экзистенциальная развилка — позиции показывают зрелость или риск регресса

### 4. Отсутствие ошибок
- [ ] Нет конфликтующих/дублирующих полей в схеме
- [ ] Все ссылки на айдишники (node_id, branch_id, case_id) валидны/актуальны

### 5. Валидность для ИИ-парсинга
- [ ] Валидный markdown/JSON, только утверждённые ключи; никаких хаотичных вставок или комментариев

---

Если хотя бы один пункт не выполнен — кейс не проходит ревью и возвращается на переработку.

## План миграции/регенерации контента кейсов

### 1. Аналитика и сегментация исходного контента

1.1. Проанализировать (автоматизированно или вручную) все кейсы старой системы:  
- Выявить полные соответствия по зависимостям id/node_id/branch_id/difficulty.  
- Оценить, какие кейсы подходят для автоконвертации, а какие — требуют реинтерпретации.

1.2. Составить карту-маппинг между старыми полями (`title`, `context`, `options`, `reflection`, `indicators`) и новыми секциями (`meta`, `portal`, `event`, `context`, `facts`, `background`, `dilemma`, `positions`, `indicators`, `reflection`).

---

### 2. Автоматическая и ручная трансформация

2.1. **Авто-парсинг**:
- Парсить существующий контент, выделяя из длинного "context" факты, описание поля (контекст), компанию, ограничения, людей и “событие/триггер”.
- Из "options" строить массив "positions", для каждой делать уточняющие промпты для доосмысления типа позиции и последствий.
- “reflection” переразметить по шаблону: вопросы — в вопросы, зеркала — в after_choice_insights.

2.2. **Вручную/с помощью эксперта ИИ**:
- Досоздавать отсутствующие секции при невозможности коррекции автоматом (особенно: event, dilemma, background, meta-индикаторы).
- Проверять полноту и глубину новых позиций — ensure, что каждый “стратегический ход” не является бытовым действием.
- Обеспечить строгий разнос “факт — интерпретация” между facts и background.

---

### 3. Валидация и бета-прогон

3.1. Прогнать все кейсы через авто-валидатор по чек-листу новой системы (см. предыдущий шаг).
3.2. Исключить или пометить красным кейсы, не проходящие по глубинным/философским/структурным критериям — отправить на ручную рецензию.
3.3. Для наиболее проблемных — привлечь архитектора/редактора ИИ для полного рерайта или комбинированного дополнения.
3.4. Протестировать новые кейсы на малой выборке пользователей (или сценарии ИИ).

---

### 4. Внедрение и поддержка

4.1. Зафиксировать новую структуру в интерактивном генераторе/редакторе кейсов.
4.2. Обеспечить описание миграции в Git/документации (pull request templates для новых кейсов/авторов).
4.3. Внедрить системные подсказки/чек-листы прямо на этап генерации и ревью.

---

- Все старые кейсы должны быть переведены, в случае невозможности — исключены или переписаны.
- Новые кейсы допускаются только в формате нового шаблона и после валидации по чек-листу.

## Новый формат “Case Card — Список” (краткая карточка)

**Визуальная цель:**  
Мини-симулятор: не просто заголовок, а входная точка в смысловую зону, провоцирует на переход в стратегическое пространство.

---

### Пример wireframe (markdown)

```markdown
┌────────────────────────────────────────────[ CASE ]─────────────────────────────┐
│ [ARCHETYPE SYMBOL] [LEVEL/ACCESS]              [META: pressure, uncertainty]    │
│────────────────────────────────────────────────────────────────────────────────│
│ TITLE: “Операционный кризис в логистике”                                       │
│ SUBTITLE: “Level III · Retention · Systems”                                    │
│────────────────────────────────────────────────────────────────────────────────│
│ EVENT/ТРИГГЕР: “Система обработки заказов упала. Давление — высокое.”          │
│────────────────────────────────────────────────────────────────────────────────│
│ CURRENT STATE:                                                                 │
│   — [✓] Пройден · Последняя позиция: “Делегировал управление”                  │
│   — [ ] Не начат · Узел допуска: [LEVEL]                                       │
│────────────────────────────────────────────────────────────────────────────────│
│ EFFECTS PREVIEW (if any):                                                      │
│   • Развивает: [Systemic vision +5%] [Resilience +3%]                          │
│────────────────────────────────────────────────────────────────────────────────│
│ [OPEN CASE →] (фокус на переход в “зал кейса”)                                │
└────────────────────────────────────────────────────────────────────────────────┘
```

---

### Ключевые UI параметры

- **Заголовок**: только смыслы бренда, никакой геймификации, минимализм.
- **Архетип/Уровень доступа**: только символы, цветовая маркировка optsidian/gold/violet.
- **Мета:** давление, уровень неопределённости (маленькие метки/бэйджи).
- **Триггер:** всегда выведено основное напряжение ситуации.
- **EFFECTS:** отображаются только для “развитых” или ключевых кейсов.
- **Кнопка:** приглашающая открыть кейс для стратегического разбора, а не как «ещё один тест».
- **Рефлексия:** отдельный ярлык/иконка, если пользователь уже прошёл рефлексию.

---

### Краткая инструкция для генерирующего компонента

1. Никогда не показывай стандартные emoji — только философские, бренд-интегрированные символы.
2. Триггер и meta — фокус первые 2 строки. Дополняется кратким пояснением current state (пройден/не начат/в работе).
3. Daй минимум декора, максимум структуры.
4. Цветовое оформление соответствует темам: obsidian, graphite, gold, amber, violet — по смысловой роли секций.
