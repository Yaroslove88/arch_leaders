## «Архитектор лидерства» — системный аудит

---

# I. 🧠 СМЫСЛ И МЕТОДОЛОГИЯ

### 1. Методологическое ядро

-  Чётко сформулировано: **что именно здесь развивается** (не “лидерство”, а какая способность)?
    
-  Есть **онтология** (ключевые понятия: субъектность, форма, поле, архитектура, интеграция, билд).
    
-  Есть различие:
    
    - между навыком
        
    - способом действия
        
    - уровнем формы мышления.
        
-  Прописано, что продукт **НЕ делает** (границы метода).
    
-  Есть внутренний документ: “Как система принимает решения”.
    

### 2. Архитектура развития

-  Описаны **уровни развития** (реактивность → интеграция → архитектура → среда).
    
-  Способности в дереве соответствуют этим уровням.
    
-  Квесты проверяют **способ действия**, а не поведение.
    
-  Evidence связано с **изменением формы**, а не “успехом”.
    

---

# II. 🎯 ПРОДУКТОВАЯ СИСТЕМА

### 3. Core loop

-  Полный цикл проживается за один день:  
    entry → разбор → изменение → квест → evidence → обновление модели.
    
-  Каждый шаг даёт **ощутимую ценность**, даже без следующего.
    
-  Нет “пустых” экранов без смысла.
    
-  Есть ощущение **движения**, а не логирования.
    

### 4. Пользовательский путь

-  Первый опыт не требует обучения.
    
-  Первый результат приходит быстро (<5 мин).
    
-  Пользователь понимает:
    
    - что произошло
        
    - что система увидела
        
    - что предлагается дальше.
        
-  Онбординг объясняет рамку, а не фичи.
    

### 5. Роли продукта

-  Продукт = зеркало.
    
-  Продукт = архитектор среды.
    
-  Продукт ≠ эксперт.
    
-  Продукт ≠ мотиватор.
    

---

# III. 🖥 UX И ИНТЕРФЕЙС

### 6. Экранная архитектура

-  Каждый ключевой экран отвечает на один вопрос:
    
    - Dashboard → что сейчас?
        
    - Session → что произошло?
        
    - Tree → как я устроен?
        
    - Quest → что пробовать?
        
    - Evidence → что реально было?
        
-  Нет дублирующих экранов.
    
-  Дерево — главный объект, а не отчёт.
    

### 7. Тон и язык

-  Нет коучинговых формул.
    
-  Нет оценок.
    
-  Нет “ты должен”.
    
-  Формулировки архитектурные, не мотивационные.
    
-  Пустые состояния содержат смысл, а не призыв.
    

### 8. Визуальная система

-  Цвета используются как состояния.
    
-  Есть глубина и пустота.
    
-  Акценты редкие.
    
-  Интерфейс не перегружает.
    
-  Дерево читается как карта, не как граф.
    

---

# IV. 🧩 ИГРОВАЯ И РАЗВИВАЮЩАЯ ЛОГИКА

### 9. Дерево способностей

-  Есть вертикальные уровни.
    
-  Есть архитектурные сцепки.
    
-  Не всё связано со всем.
    
-  Есть “потолки”.
    
-  Есть интеграционные состояния.
    

### 10. Квесты

-  Квест = эксперимент.
    
-  Есть гипотеза.
    
-  Есть критерии evidence.
    
-  Есть trade-offs.
    
-  Не больше 5 активных.
    
-  Есть причины появления квеста.
    

### 11. Билды

-  Билды обнаруживаются, а не выбираются.
    
-  Есть бонусы и ограничения.
    
-  Билд влияет на интерпретацию ситуаций.
    
-  Можно выйти из билда.
    

---

# V. 🤖 AI И АНАЛИТИЧЕСКИЙ ДВИЖОК

### 12. Интерпретация

-  Система извлекает не только темы, но и **способ действия**.
    
-  Есть промежуточные сущности (паттерны, напряжения, сигналы).
    
-  Есть версия пайплайна.
    
-  Есть fallback режим.
    

### 13. Объяснимость

-  Каждый квест знает “почему”.
    
-  Каждое изменение дерева знает “на основе чего”.
    
-  Есть rationale.
    
-  Есть ссылки на evidence.
    

### 14. Контроль качества

-  Есть re-run.
    
-  Есть dry-run.
    
-  Есть undo.
    
-  Есть лог LLM-запусков.
    
-  Есть мониторинг ошибок.
    

---

# VI. ⚙️ СИСТЕМА И АРХИТЕКТУРА

### 15. Данные

-  Сырые данные не затираются.
    
-  Анализ версионируется.
    
-  Состояние отделено от событий.
    
-  Есть changelog.
    
-  Есть audit log.
    

### 16. Операционка

-  Есть админ-панель.
    
-  Есть User 360.
    
-  Есть очередь.
    
-  Есть алерты.
    
-  Есть экспорт.
    

### 17. Безопасность и этика

-  Разграничение прав.
    
-  Маскирование данных.
    
-  Причины доступа к приватному.
    
-  Пользователь может удалить/экспортировать данные.
    
-  Нет терапевтических обещаний.
    

---

# VII. 📊 МЕТРИКИ И СИГНАЛЫ ЗРЕЛОСТИ

### 18. Продуктовые метрики

-  % пользователей, дошедших до первого цикла.
    
-  Частота entries.
    
-  Доля закрытых квестов.
    
-  Возврат через 7 / 30 дней.
    
-  Частота undo.
    

### 19. Методологические метрики

-  Рост интегрированных узлов.
    
-  Снижение хаотичных entries.
    
-  Изменение языка пользователей.
    
-  Уменьшение “пожарных” квестов.
    

---

# VIII. 🧭 СТРАТЕГИЧЕСКИЕ ВОПРОСЫ

Ответь себе письменно:

-  В чём продукт станет **незаменимым**?
    
-  В чём он будет **опасен**, если ошибётся?
    
-  Что произойдёт, если человек будет использовать его 2 года?
    
-  Что продукт делает с ответственностью пользователя?
    
-  Как выглядит «зрелый пользователь» в поведении?
    

---

# IX. 🚩 КРАСНЫЕ ФЛАГИ

Отметь, есть ли сейчас:

-  желание добавить фичи вместо углубления логики
    
-  квесты, которые выглядят как задачи
    
-  дерево, которое можно “прокачать”
    
-  тексты, похожие на курс
    
-  решения, которые нельзя объяснить
    

Если ≥2 — это сигнал остановиться и чинить ядро.

1. Пройти все блоки.

    - 3 системных долга
        
    - 3 архитектурных риска
        
    - 3 точки силы.

    (например: explainability, квесты, дерево, онбординг, аналитика).
